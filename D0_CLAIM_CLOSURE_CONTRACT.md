# D0 Claim Closure Contract

`bridge` is not a positive closure status.

## Forbidden

- `BRIDGE-CLOSED` without proved hypotheses.
- `CONDITIONAL-CLOSED` as a status upgrade.
- `external theorem applies` without proof that all external hypotheses hold for
  the D0 object.
- `sample cert passed` as proof of an infinite family.
- `negative controls passed` without a stated failure theorem or finite scope.

## Allowed Closure Statuses

- `LEAN-THEOREM-CLOSED`
- `FINITE-CERT-CLOSED`
- `INFINITE-FAMILY-PROVED`
- `EXTERNAL-THEOREM-APPLIED-HYPOTHESES-PROVED`
- `EMPIRICAL-PASSPORT-CLOSED`
- `NO-GO-CLOSED`
- `OPEN`

## Reduction Statuses

These are not closure statuses:

- `THEOREM-AVAILABLE / D0-HYPOTHESES-OPEN`
- `REDUCED-TO-HYPOTHESES`
- `PASSPORT-SAMPLE-EVIDENCE`
- `FINITE-PASSPORT-CERTIFIED / INFINITE-FAMILY-OPEN`

## Rule

A claim is closed only if it is a theorem, a complete finite cert, an external
theorem with all D0 hypotheses proved, an empirical passport within its declared
data scope, or a no-go/boundary theorem.

Any remaining bridge is a proof obligation.

## Value is a required field, not a commentary

Closure says how well a claim is proved. It does not say whether proving it was worth anything.
A corpus that records only closure sorts itself by bookkeeping: its front door opens on whichever
module has the loudest name, and effort flows to whatever is cheapest to close rather than to what
matters. Value is therefore a second, orthogonal, **computed** axis, and it is maintained under CI
exactly like the status map.

- **Every claim carries a value score** in `09_LEAN_FORMALIZATION/docs/D0_VALUE_LEDGER.csv`,
  regenerated by `tools/d0_value_model.py` and enforced live by `tools/check_value_ledger_sync.py`.
  A new result is not finished when it builds — it is finished when it is proved in Lean or by a
  can-fail certificate, entered in the registry, **and ranked**.
- **Four components are computed** from the corpus itself: structural weight in the derivation
  chain, semantic load of the formal statement, falsifiability reach, foundation position.
- **One component is declared**: external significance, in
  `03_THEORY_MAP/D0_EXTERNAL_SIGNIFICANCE.csv`. Every declared weight must name the external
  question it answers and cite a source, so it can be disputed row by row. A weight of 3 on a claim
  that ranks as ballast is a CI failure: either the weight is inflated or the claim is
  under-connected, and which one must be written down.
- **The quadrants are the work plan.** High value + closed is the front door and the only material
  admissible in an abstract. High value + open is the **attack queue** — the ranked campaign list.
  Low value + closed sorts to the bottom of the registry. Low value + open is a retirement
  candidate, never a campaign target.

Effort spent outside the attack queue is bookkeeping and must be labelled as such.

## The derivation chain

The registry is a list; the theory is a chain. `tools/d0_logic_chain.py` builds the real derivation
DAG from Lean `import` edges — the only machine-truthful record of what rests on what — and stamps
each claim with a content hash and a `block_hash = sha256(content_hash ‖ parent block hashes)`.

- A claim that imports no other D0 module is a **genesis block**: it rests on Mathlib alone.
- Editing the *content* of an upstream module changes every downstream block hash, so "this claim
  was verified against that version of its foundation" becomes checkable instead of assumed.
  Docstring edits do not propagate: hashes are taken over comment-stripped source.
- A cycle in the DAG is a hard CI failure: a claim cannot transitively rest on itself.

Chain depth is the honest measure of how much has actually been *derived* as opposed to merely
*collected*. A corpus of many genesis blocks is wide, not deep; connecting islands raises depth,
and depth is what a foundational claim ultimately rests on.

## CVFT operator hardening

Closed-vacuum feedback closure may use `F_N=P_NU_N^\dagger Q_NU_NP_N` only as
feedback-return and `R_N=D_N^\dagger D_N` only as positive response/readout.
Feedback pressure is `P_fb=beta^{-1}d_V log Z_N`; `P_N` is never pressure.

Allowed feedback claims require the positive identities, the correct resolvent
domain and the logarithmic determinant trace expansion. Forbidden shortcuts are:
`Q_N\ne0 -> F_N\ne0`, determinant trace without `-\log det`, complex
mass/width poles from bare positive `F_N`, root/window/H0/Omega_m/rd refits,
arbitrary-kernel SPARC/DESI repair and empirical promotion without a pinned
passport.

## Development / release split

The full hard closure is a release gate, not the normal theorem-development loop.

Allowed development loop:

```text
edit active theorem module
→ build active module
→ build ActiveClosureIndex
→ run only touched certificates
```

Required release loop:

```text
build HardClosureTheoremIndex
→ run all hard certificates
→ check claim map coverage
→ check no forbidden sorry/axiom/Float in protected layers
→ rebuild release ledger
```

Previously proved theorems must be imported through stable interface modules whenever possible.  Editing a low-level core module invalidates the downstream DAG and is permitted only when the primitive itself changes.

Closure is monotonic only at the interface boundary: once a theorem is frozen, downstream active modules depend on its statement, not on rewriting its proof body.

Lean verification is not required after every prose or cert edit. During active
integration, use fast guards first and queue touched Lean targets. Run Lean in a
deferred phase through `tools/lean_dev.ps1`, with `.lake` stored externally and
checked by `tools/check_lean_storage_hygiene.ps1`.
