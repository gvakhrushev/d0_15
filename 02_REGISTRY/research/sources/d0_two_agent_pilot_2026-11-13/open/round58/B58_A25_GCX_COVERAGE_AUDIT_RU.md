# B58. Структурное покрытие A25 компилятором A29

Статус: **PASS структурного покрытия закреплённой версии A25/A29**, не путать с исполнением полного гигантского потока. Проверяемый компилятор: `direct/round29/gcx_compiler.py`, SHA-256 `7171c4f992376a3bdface4563156c881dbfd485048980b0d3dc62ef11addf0fa`. Он сначала распознаёт целую A13 CZ, затем транслирует оставшиеся SourceI попарно с переносом состояния через `seq/repeat/stream`. Вывод обоснован структурной индукцией по реальным провайдерам и отдельными конечными проверками, а не попыткой развернуть всё W.

## 1. Индуктивный класс остаточных слов

Назовём слово good, если каждый максимальный последовательный run SourceI имеет чётную длину. Good замкнут относительно конкатенации и `repeat`: на стыке два чётных run остаются чётными. Маршрут `remap_native` только переименовывает провода и сохраняет порядок и дерево. Literal inverse good-слова тоже good: порядок обращается; каждый SourceI заменяется тремя, поэтому длина каждого старого чётного run умножается на 3; `CX^-1=CX`; при `G^-1` добавляются только чётные `SourceI²` с обеих сторон G и, для не-port target, дополнительные CX. Следовательно это верно для **любого целого** inverse depth, включая повторные обратные вызовы внутри адаптера, а не только для depth 0/1. Все глобальные SourceI обращаются к одному отображённому `(port,spin)`.

Отдельная исключительная метка — полное A13 CZ. Его явный native subtree содержит 19 детей в production-варианте: 14 CX и 5 одиночных SourceI. При каждом буквальном inverse сохраняется корень `seq`, порядок обращается для нечётного depth, каждый из пяти SourceI становится вложенным `repeat(3,...)` кратности `3^depth`. Это именно форма, распознаваемая `exact_cz` до спуска в детей; далее весь CZ заменяется на один gadget. Исходные source IR, remap и inverse не сплющивают этот `seq`.

Ложного срабатывания в good-частях нет: шаблон целой CZ содержит **внутренний** нечётный SourceI-run между CX, который нельзя исправить соседними блоками снаружи его дерева. Снаружи CZ рассмотренные ниже производители выводят good-слова. В REPORT реальные CZ возникают только в `copy_SELECT` внутри `pair_ir`; другие logical операции — X/H/CX/CCX/Z без CZ. Родительский recognizer проверяет не один count, а точный порядок всех CX, пять одинаковых нечётных кратностей и точные port/spin. После распознавания он не спускается внутрь CZ.

Транспортер SourceI parity в A29 хранит pending через каждую границу `seq`, `repeat`, и между блоками `stream`, что необходимо для SC6, где два отдельных листа SourceI могут лежать в разных блоках. Поскольку после удаления полных CZ остаток good, он не встречает несочетанный SourceI перед G/CX или конечным остановом. Реализация `repeat` использует конечное состояние, без развёртки показателя.

## 3. Точное число CZ и новых стадий

Независимым проходом настоящего `walk_events` получены 455 записей Hf и 18 записей Hq. Каждая Hf-запись содержит 82 CZ, каждая Hq — 4. В одном report есть два Hf и восемь Hq:

```
CZ_per_report = 2·455·82 + 8·18·4 = 75 196
A: 7·75 196 = 526 372
W: 526 372 depth0 + 526 372 depth1 = 1 052 744
```

Эти production CZ содержат вместе **10 527 440 SourceI** (`5` на forward и `15` на inverse) и **14 738 416 CX**. READY compute/uncompute не содержит CZ. Полный census: [код](cz_occurrence_census.py), [результат](CZ_EXACT_OCCURRENCES.json).

При `S_old` SourceI в опубликованном *локальном* A25 inventory, `C=1 052 744`, `P=(S_old−10 527 440)/2` пар и сертифицированном B57 положительном k, новый платный учёт равен

```
G_new  = G_old + 16 k P + 32 k C
CX_new = CX_old − 6 C + 2 P
rotations = 2 P + 4 C < 2^4188
```

Первая замена использует `G^(4k), G^(12k)` и 2 CX; вторая — `G^(2k), G^(14k), G^(14k), G^(2k)` и 8 CX. Независимый пересчёт совпадает с A29: `L_new` имеет **11647 бит**, SourceI отсутствует, число новых RAW-рождений 10 407 050 782: [код](audit_a29_counts.py), [результат](A29_INDEPENDENT_COUNTS.json). B57 даёт строгую условную all-column ошибку замен `<2^-3244`. Это оценка нового полного word на тех же input факторах после добавления helper, а не эквивалентность часов и исходных меток.

## 4. SAM и старый фактор

В исходных A25 G/CX **каждый** SAM-провод либо не участвует, либо является CX control; G и CX никогда не нацелены на SAM. Это следует из ролей всех source emitters и проверенных disjoint layouts; literal inverse также не создаёт SAM-target. Новые Z/CZ gadgets используют прежние port/controls и свежий helper как targets, так что это свойство сохраняется на каждом примитиве. После замены всех SourceI старые **логические** placeholders 0 и 1 не адресуются; old witness 3 не адресовался и ранее. Новое переименование физических RAW-координат не является reset этих старых факторов: при `m=0` физический провод 0 — новый port, а не старый logical 0.

Отсюда для контракта со свежими aux и helper, включёнными в RAW-сжатие, вещественная глобальная матрица, точный control-only SAM и тождество на оставленном `D_old` дают точный вещественный scalar corner в каждом SAM-секторе. Это не требует `W_new²=I`, и B52-доказательство на произвольном внешнем aux не применяется без дополнительных условий.

Ни полное физическое разрешение births/G/CX, ни старый `P0`, ни привязка исходных marked prefixes, readers, heat или Cost−Info здесь не устанавливаются. `physical_C_closed=false`; `GR_closed=false`.
